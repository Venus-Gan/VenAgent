# VenAgent 选择性重构路线规范

## 目标

VenAgent SHALL 以 `AGI-saber` 为功能、行为和风险参考，按模块逐个进行审计、取舍、设计、审批、实现和验收，不进行源码迁移、固定阶段打包或一次性全量重构。

旧项目存在某项能力不代表 VenAgent 必须实现该能力。每个候选模块均允许整模块舍弃、只采用部分内容，或用完全不同的技术方案实现同一产品目标。

## 架构不变量

- 运行时编排 SHALL 使用 LangGraph；模型和工具适配 SHALL 使用 LangChain 公开边界，除非未来独立架构 change 明确替换。
- Web/API、应用服务、图运行时、领域能力、Ports 和 Adapters SHALL 保持可识别边界。
- 对话线程、checkpoint、长期语义记忆、用户偏好、任务状态、文档和运行事件 SHALL 分别建模，不因旧项目混用而继续混用。
- 外部服务失败不得伪装成真实成功；降级状态 SHALL 可测试、可观察。
- 新模块 SHALL 默认提供无网络、无真实凭据的验证路径。
- 已完成的最小 Agent Loop、真实模型适配器和基础 Web UI 构成当前基线，不因路线重排自动回滚。

## 路线单位

路线的实现和审批单位 SHALL 是“模块”，不是固定 Phase。

每个模块进入 Build 前 SHALL 单独完成：

1. 审计 `AGI-saber` 中与该模块有关的实现、行为、依赖、测试和已知风险。
2. 审计 VenAgent 当前边界，确认已有能力与缺口。
3. 把旧模块拆成可独立取舍的子能力，避免整包默认迁移。
4. 为模块和子能力记录明确取舍。
5. 定义目标行为、范围、非目标、接口、迁移边界和验收标准。
6. 取得用户对该模块当前完整契约的明确批准。
7. 使用独立 Comet Native change 实现、验证和归档。

一个模块完成后，由用户决定下一个模块；候选目录获批不构成任何模块的实现授权。

## 取舍状态

每个候选模块及其重要子能力 SHALL 使用下列状态之一：

- `adopt`：目标与主要方法均采用，但仍按 VenAgent 架构重新实现。
- `partial`：只采用明确列出的部分，其余内容进入舍弃或延期清单。
- `replace`：保留产品目标，放弃旧实现方法，使用单独批准的新方案。
- `drop`：明确不进入 VenAgent；后续不得因旧项目存在而自动恢复。
- `defer`：当前不实现，只有新的收益或依赖证据出现后才重新评估。

状态必须附带简短理由、选中的子能力、明确排除项和依赖影响。模块状态可以通过新的路线修订 change 改变，但不得在实现过程中静默漂移。

## 由简至繁的候选模块目录

下列稳定编号表示推荐审计和实施顺序，不是批量审批阶段。每个模块仍可选择 `adopt`、`partial`、`replace`、`drop` 或 `defer`；跳过模块不要求补齐编号，但后续模块必须重新检查真实依赖。

1. `M01 conversation-context`：`thread_id`、有限多轮上下文、线程隔离和进程内 checkpointer。
2. `M02 streaming-run-lifecycle`：SSE 事件、token 流、目标运行取消、断开和错误契约。
3. `M03 conversation-persistence`：conversation/checkpoint 持久化、重启恢复、迁移和清理。
4. `M04 ownership-lifecycle`：可选身份、`owner_id` 隔离、授权边界和数据保留生命周期。
5. `M05 user-preferences`：显式或规则化偏好、查看、修改、删除及受控提示注入。
6. `M06 basic-tool-loop`：最小模型→工具→模型循环、结构化结果、步数和超时边界。
7. `M07 semantic-memory`：长期事实候选、存储、召回、来源和上下文预算。
8. `M08 memory-governance`：记忆安全、冲突、quarantine、superseded、审计与删除。
9. `M09 mcp-integration`：受控 MCP 注册、传输、endpoint 策略和响应边界。
10. `M10 sandbox-approval`：隔离执行、最小权限、高风险动作审批和文件/命令边界。
11. `M11 document-ingestion`：文档模型、上传、解析、切分、版本、删除和重建。
12. `M12 baseline-rag`：单一可测试检索路径、上下文组装、引用和离线质量基线。
13. `M13 advanced-retrieval`：按评测证据选择 query rewrite、rerank、hybrid 或父子检索。
14. `M14 task-planning`：显式任务状态、计划、步骤依赖、进度和串行恢复。
15. `M15 reliable-parallel-runtime`：幂等、重试、checkpoint 恢复、并行调度和部分失败。
16. `M16 subagents-artifacts`：隔离子 Agent、预算、结果契约、workspace 与产物交付。
17. `M17 skills-extensibility`：按收益和安全边界选择 prompt、manifest 或受控插件机制。
18. `M18 platform-governance`：全局评测、性能、部署、备份恢复、API 治理和供应链策略。

Web UI、API、测试、安全和可观测性不是被排到 `M18` 的欠账。每个模块 SHALL 同时交付自身所需的最小端到端体验；`M18` 只处理跨模块的平台级治理。

模块目录可以通过新的路线修订 change 继续拆分、合并、改名、舍弃或增加，但编号与依赖变化必须显式记录，不得在模块实现中静默改变。

## 依赖与顺序

- 默认审计和实施顺序 SHALL 遵循 `M01...M18` 的由简至繁排序；明确的能力依赖优先于编号。
- 依赖必须写成可验证关系，例如“持久化 checkpoint 依赖稳定的线程身份契约”，不能只写“通常先做”。
- 没有硬依赖的模块可以跳过、延期或调整顺序。
- 如果较早模块被 `drop` 或 `replace`，所有声明依赖它的后续模块 SHALL 在进入 Shape 前重新审计依赖并调整方案。
- 一个大型模块如果包含可独立交付部分，SHALL 优先拆小，避免把无关内容绑定审批。
- 基础模块不得以“以后可能需要”为理由预建尚未选择的复杂扩展点。

## 随模块交付的横切内容

Web UI、安全、测试和可观测性不 SHALL 被统一延期到最后一个产品化阶段。

每个被选择模块必须同时定义并交付它实际需要的：

- 最小 Web/UI 入口和用户可见状态；
- 稳定 API、事件或错误契约；
- 与风险相称的安全边界；
- 离线单元、集成或端到端验证；
- 能区分成功、失败和降级的最小观测证据。

全局部署、性能治理或供应链工作仍可作为独立模块，但不得替代各功能模块自身的完成条件。
