# Outcome

把 VenAgent 从固定 Phase 1–7 的批量路线改为逐模块选择性重构：每个模块单独审计、取舍、设计、审批、实现和验收；允许整模块舍弃、只采用其中部分内容，或以完全不同的技术方案实现同一目标。

# Scope

- 以已归档的 `define-refactor-roadmap` 审计和 canonical `refactor-roadmap` 规格为可追溯基线。
- 把原 Phase 1–7 拆成可独立决策的模块候选池。
- 为每个模块定义采用、部分采用、替换实现、舍弃和延期五类取舍结果。
- 用真实依赖关系决定先后，不以旧 Phase 编号自动决定实现顺序。
- 按复杂度和依赖把候选模块稳定排序为 `M01...M18`，从最小会话基础逐步走向复杂编排与平台治理。
- 明确每个模块的 UI、API、安全、测试和可观测性应随模块交付，而不是统一拖到最终产品化阶段。
- 在修改完成后产出一份完整替换规格，而不是增量补丁。
- 保持随后创建的 `phase-1-conversation-runtime` 停留在未批准 Shape，不继续实现。

# Non-goals

- 不修改已经完成的 Phase 0、最小 Agent Loop、LLM 配置或当前 Web UI 实现。
- 不在本 change 中实现任何 Phase 1–7 功能。
- 不删除或改写已归档的历史、验证证据和审计报告。
- 不把现有 Phase 1 专项草案视为新路线的既定内容。

# Acceptance examples

- 用户可以对“长期记忆”选择部分采用，对“图记忆”选择舍弃，对“持久化”选择另一套技术方案，且三项分别记录、互不绑架。
- 一个模块只有在专项审计和用户批准后才进入实现；旧项目存在该模块不构成实现理由。
- 模块实现完成时，它所需的最小 Web/API、测试、安全和观测行为同时完成，不遗留到统一的 Phase 7。
- 模块顺序由已确认依赖决定；无依赖模块可以延期或跳过，不需要补齐前置 Phase 编号。
- 候选目录按由简至繁排列；跳过某模块后，后续模块必须重新检查依赖而不是假定它已经实现。
- 用户明确批准新路线前，不启动或恢复任何阶段实现。
- 旧归档仍可用于比较“原路线 → 新路线”，但不再代表当前待执行路线。

# Constraints and invariants

- `AGI-saber` 继续只作为行为与风险参考，不作为源码迁移目标。
- 每个模块仍需独立 Comet Native Shape 和用户确认；模块目录获批本身不授权实现。
- 已完成 Phase 0 保持不变，除非用户后续明确要求另开 change 修改。
- 修改必须保存为 `refactor-roadmap` capability 的完整目标规格，并区分“候选模块”与“已选择模块”。
- 不直接编辑归档状态、approval、证据哈希或 Runtime 管理字段。

# Decisions

- 使用新的 `revise-refactor-roadmap` replace change 表达回退和修订，不反归档或篡改原证据链。
- `phase-1-conversation-runtime` 未进入 Build、没有实现代码；在新路线获批前保持冻结。
- 固定 Phase 不再是实现或审批单位；每个模块单独建立 change。
- 取消原 Phase 1–7 编号，以按复杂度排序的稳定模块编号 `M01...M18` 代替；模块编号不构成批量授权。
- 模块审计必须允许五种结论：采用、部分采用、替换实现、舍弃、延期。
- 跨模块能力不统一拖到最后：属于某模块的 UI、API、安全、测试和观测内容随该模块完成。
- 用户已确认模块化治理、取消 Phase 1–7、`M01...M18` 由简至繁排序，以及 Web UI 随模块逐步完善的完整路线契约。

# Open questions

无。

# Verification expectations

- 对比旧 canonical 与新拟议规格，确认固定 Phase 执行授权已被逐模块治理替代。
- 检查模块边界、依赖、取舍状态、非目标和出口门槛不存在自相矛盾。
- 确认本 change 没有修改运行时代码、配置、测试和 Phase 0 行为。
