## Question

工具调用失败要在前端可见（不只是"成功操作"）。范围：TrajectoryPanel / 操作列表如何展示失败的 operation（失败 status、error_code、错误摘要），审批被拒 / 命令超时 / 沙箱错误等路径的呈现。**延后**：涉及 Web 改造，与后续其他修改（多工具、轨迹扩展）合并做；本票在 `剩余功能规划` 定稿后才有资格开工。

## Resolution（RESOLVED，2025-07 用户 4 问拍板）

### 决策（T1-T4）

- **T1 失败呈现形态**：错误码徽标 + 错误摘要 + 可展开详情。失败态（is-error 样式已有）上增加：error_code 徽标（如 `command_timeout`）+ 失败时 result_summary 作为第一行优先展示（成功时维持现状）+ 单条 operation 可展开完整错误详情。
- **T2 契约边界**：前端补 error_code 透传（store.ts 类型+映射+渲染，后端 OperationResponse 已具备零后端改动）；**失败摘要保证**——规范要求失败 operation 的 result_summary 必须含可读错误摘要（exec_command 错误截断内容 / 命令超时 / 沙箱错误均写入 result_summary，失败时 operation 层不静默；实现时核查各路径，缺失则后端补）。
- **T3 三路径呈现**：**分路径专属文案**（用户拍板，推翻「统一通用呈现」推荐）：审批被拒 / 命令超时 / 沙箱错误各写专属文案；未知 error_code 回落通用文案。
- **T4 时机与交互**：本票 resolve = 呈现规范定稿；实现并入多工具/轨迹扩展阶段（M06 放开时与前端一起动）；交互只读，重试/恢复属 M07 不做。

### 呈现规范（实现时按此展开，随多工具阶段落地）

1. **分路径文案映射表**（status/error_code → 文案，实现时核实现有 error_code 全集后定稿）：
   - `rejected` → 「审批被拒」+ 风险原因（riskReason）
   - `error_code == "command_timeout"` → 「命令超时」
   - 沙箱错误路径（实现时确认 error_code 值，如 `sandbox_error`）→ 「沙箱错误」+ 摘要
   - 其他失败 → 通用「执行失败」+ error_code 徽标原文（未知 error_code 回落此档，不写死文案）
2. **失败 operation 行**：statusClass(is-error) + error_code 徽标 + result_summary（失败摘要优先行）+ 展开区（完整错误详情：error_code、result_summary 全文、artifacts）。
3. **展开交互**：单条 operation 展开/收起；默认折叠，失败态默认展开（或徽标旁「详情」按钮）。
4. **契约落实**：store.ts ProcessingEvent 加 `errorCode: string | null`；映射 `errorCode: item.error_code`；TrajectoryPanel 渲染徽标与展开区；SSE `tool` 事件与 `/api/operations` 同源字段。
5. **失败摘要保证核查**：实现时逐一核查 exec_command 错误截断 / 命令超时 / 沙箱错误三条路径 operation.result_summary 写入；缺失路径后端补（写入点：tools/operation_store.py 失败终结路径）。

### 验证（随多工具阶段 Verify 一并执行）

- `/api/operations` 与 SSE 两路消费均呈现一致错误信息（同源字段）。
- 失败摘要保证：三条路径 operation.result_summary 均有可读内容（无静默失败）。

### 验证补充（2026-08，Playwright 端到端验证发现，已定位未修复）

- **现象**：run 执行期间，前端在 SSE 长连接（`GET /api/runs/{id}/events` 已挂接且 200）**之外**，仍以 300–800ms 间隔双轮询 `GET /api/operations` + `GET /api/runs/{id}/event-log`；一次真实 run（34s）产生约 40 轮 ≈ 80+ 请求，两端点各自拉全量（event-log 全量历史、operations 全量列表）——双重获取、无退避。
- **定位**：事件数据经 SSE 已可完整推送（streaming.py tool/approval 事件带完整 payload），轮询属冗余补状态；多工具放开后每步一审批，轮询频率将随工具调用数线性放大，且与 T4 轨迹扩展（error_code/展开交互）同处前端 store/面板层。
- **处理**：与 T4 呈现规范一并修复（多工具/轨迹扩展阶段）：评估以 SSE 事件为唯一状态源 + 轮询降频/退避/仅在事件缺口时补拉；实现时纳入多工具 Verify 网络请求计数检查。此条为遗留优化，不阻塞 M06 基线。

### 实现落地与呈现修订（2026-08-28，用户逐项拍板）

T1–T4 呈现规范已随多工具阶段实现（`web/src/modules/chat/` store/ChatWorkspace/TrajectoryPanel/style.css + E2E），实现中对 Resolution 有如下修订与补充，以本节为准：

- **T1 呈现形态修订（推翻独立错误气泡）**：run 级失败不再渲染独立红色错误气泡；失败/取消挂在 **think 活动块**上（标红 + 红点 + `role="alert"` + 点击展开 terminalMessage 详情）。operation 失败由 tool_call 节点自身承载（头部专属文案 + error_code 徽标，展开看错误码/完整摘要/参数/风险/artifacts）。`role="alert"` 随失败活动块保留。
- **error_code 全集核实（T3 预留项收尾）**：网关超时实际码为 `tool_timeout`（非 Resolution 假设的 `command_timeout`，后者是 sandbox 内命令超时码）；前端文案映射两者同义 →「命令超时」。`approval_rejected`→审批被拒+风险原因、`sandbox_` 前缀→沙箱错误、cancelled→已取消、未知回落「执行失败」均按 Resolution 落地。
- **think 块生命周期（新拍板，扩充 T1 范围）**：思考活动块与 run 同生命周期——运行中「思考中」（脉冲点 + 折叠行滚动显示最新思考增量，展开显示全部），成功后保留「思考完成」（展开看思考内容，无内容显示占位），失败/取消标红承载错误。思考内容统一由 think 块承载，最终 assistant 消息内不再重复注入 reasoning 行。工具调用与 skill 折叠态保持名称可见。
- **reasoning 内容缺口（已探查，用户拍板不桥接）**：DeepSeek Responses wire 上有完整思考（`response.reasoning_text.delta`），但 langchain-openai 1.4.0 明确不提取 reasoning_content/Responses reasoning（官方文档建议 provider 专用子类）。前端已做时序加固（终态抢救流式 reasoning + 事件日志重建不用空覆盖）；接受「本次运行没有返回思考内容」占位，将来升级 langchain-openai 或引入 provider 集成后前端无需改动。**决策：不做 monkey-patch 桥接。**
- **审批可见性（实现发现的缺陷修复）**：原实现聊天流只渲染终态 operation，`awaiting_approval` 期间对话流无任何提示、无法审批。已改为非终态 operation 也渲染 tool_call 节点，待审批默认展开并内联批准/拒绝按钮。
- **关联决策提醒**：`取舍原则复核` 已拍板「authorize_tool_run 移出 bootstrap」——本次修复的 `RunGrantInvalid` 根因（bootstrap.py 内 `adapters` 变量被后续 CommandRegistry 列表遮蔽 → 授权查询 AttributeError 被静默吞掉 → 伪装越权，工具 run 必失败）正是该函数；bug 已修并补分类日志（授权异常/owner 不匹配/缺 tool.invoke/快照绑定不匹配分记 ERROR/WARNING），**「移出 bootstrap」决策已于 2026-08-28 执行**（见下方遗留③已解决条目）。附带修复：langchain 聚合层过滤 provider 空工具调用骨架、tool_call id 缺失合成 uuid、坏参数 JSON 修复路径（`tools/langchain.py`）。
- **验证结果**：Playwright E2E 20 passed（mock）；真实环境（durable + PostgreSQL/Neo4j + DeepSeek）验证 echo 批准成功 / 拒绝 → `approval_rejected`+原因落库 / `sleep 60` → `tool_timeout`、run 级失败 alert 气泡 → 活动块承载、轨迹展开/收起、刷新持久化恢复、LLM 401 失败注入无密钥泄露。
- **遗留（未修，待排期）**：① `SandboxUnavailable` 间歇失败（Windows Docker 创建容器偶发超时，环境相关）；② Git Bash 启动被 `__COMPAT_LAYER` 触发配置白名单快速失败（PowerShell 不受影响，是否放宽 env 白名单未拍板）。
- **遗留③已解决（2026-08-28）：SSE 双轮询优化落地**。SSE 为唯一状态源：`run_event` 帧增量应用 operations（按 operationId upsert，`kind`→OperationRecord 状态机映射）与轨迹（按 sequence 去重排序；RunEvent→TrajectoryEvent 映射抽 `mapRunEvent` 与全量 loadProcessing 共用，杜绝两套映射漂移）；`tool`/`approval` 帧为同一条 RunEvent 的双份编码，直接跳过；全量回拉只保留建流前 / 流结束校对 / 历史加载 / 审批决定后四个低频时机（单 run 约 3–4 次，旧行为每事件 2×GET、34s run 80+ 请求）。event-log 的 `after_sequence` 游标评估后不启用：operations 无对应游标，混合增量会引入 merge 不一致，全量校对一次/run 足够。E2E 新增网络计数用例（`requestCounts` 断言两端点各 ≤4 次/run）+ `runEvent` 受控流发射能力；E2E 21 passed、非集成 pytest 383 passed。**同批执行：`authorize_tool_run` 移出 bootstrap（取舍原则复核遗留决策）**——新建 `ownership/authorization.py` 的 `RunAuthorizationPolicy`（窄 Protocol + 策略类，三条失败路径与日志分级原样迁移），bootstrap 组合根改一行绑定，`adapters` 遮蔽警示注释随之删除；补策略单测 4 例 + gateway `RunGrantInvalid` 契约 1 例（此前零覆盖）。
