## Question

用户观察：长期记忆目前「每轮都存」——`agent/runtime.py` 每个 run 完成后为该条用户消息入队 extract job（`memory/jobs.py` enqueue_extraction，幂等 key=source_ref），后台 `MemoryMaintenanceWorker` 每秒 claim 后用 `LangChainMemoryExtractor` 对**单条消息**跑 LLM 抽取，经 `LongTermWriter` 写入事实库（槽位合并/隔离），再 enqueue embedding 索引。显式「记住…」另走同步路径。

用户方向：长期记忆要跟短期记忆（conversation turn 选择 + 确定性摘要，每轮零成本）明确区分，**异步 N 轮后再沉淀写入，不要每轮都抽取**。

需拍板的决策：

1. **触发策略**：按轮数 N（批量窗口）？会话边界（新会话开始/空闲超时 flush）？时间窗口？混合？各自的失败恢复语义（进程重启、job 队列已有 retry/fencing）？
2. **抽取输入粒度**：维持单条消息多次抽取，改为聚合约 N 条消息一次 LLM 抽取？冲突纠正（第 k 轮说 X、第 k+2 轮改口）在延迟批量下如何自然合并（现有 decide_merge/supersede 是否够用）？
3. **显式记忆**：「记住…」自然指令是否保持同步即时写入（现状 process_natural_intent）？
4. **短期/长期边界术语**：新策略下两层记忆的命名与语义钉词（短期=确定性上下文装配，长期=异步沉淀事实）。
5. **改动面**：job 粒度变化对既有幂等 key / retry / fencing / 测试的影响范围。

业界参考（research 产物 `assets/长期记忆写入策略-研究.md`）：mem0、Letta/MemGPT、Zep/Graphiti、LangGraph Store/memory 模式、ChatGPT Memory、Anthropic memory tool 等。

约束：单进程 asyncio（不引入 Kafka/外部总线，Out of scope 已钉）；不重建 temporary 镜像；PG job 队列与 capability registry 语义保留。

## Resolution

（2026-08-29，用户两轮 grilling 拍板 6 项；research 产物 `../assets/长期记忆写入策略-研究.md` 交叉核对全部吻合。）

- **D1 触发形态 = 计数窗口 + 空闲兜底，先到先触发**：攒满 N 条用户消息触发沉淀；会话静默超过空闲阈值（默认 10 分钟）由现有 `MemoryMaintenanceWorker` 轮询扫描兜底（一条廉价 SQL，无新组件）。**不做**「新会话边界」触发事件（空闲兜底覆盖其需求，少一条触发路径）；**不加**研究建议的「最迟时限 T」守卫——计数窗口本身即 pending 存留的最迟条数上界，两条件互相兜底（对研究方案的 conscious 简化）。
- **D2 显式记忆保持同步即时写**：「记住…/忘记…」自然指令继续走 `process_natural_intent` 同步路径，权威回复契约（saved/rejected）不变。业界双轨惯例佐证：ChatGPT saved memories 即时写、Claude memory tool、mem0 显式即时。
- **D3 抽取粒度 = 窗口聚合一次 LLM 抽取**：严禁 flush job 内按单消息循环跑 LLM（研究反模式第 5 条）。窗口内同槽位以最后一次陈述为准（抽取提示词规则），窗口内改口不产生中间态事实；decide_merge/quarantine/supersede 职责收敛为**跨窗口**冲突合并，链路本身不变。
- **D4 抽取输入 = 用户消息为主 + 助手回复作上下文**：事实只允许从用户陈述取；助手回复进提示词仅辅助指代消解，不作为事实来源。
- **D5 pending 状态 = PG 游标**：conversation 级「已沉淀到 sequence=X」游标 + 触发状态，不复制消息内容；沉淀 job 从 conversation 按游标续读，重试整批重跑靠 decide_merge 幂等收敛；复用现有 PG job 队列 retry/fencing。runtime 每轮不再入单消息 extract job。
- **D6 短期/长期分层语义**：短期 = 近期 turn + 确定性摘要（现状不动，每轮零成本装配）；长期 = 沉淀产物。接受的可视性变化：窗口内新事实暂不在长期 recall——本会话由短期记忆承接，跨会话召回最多延迟 N 条或空闲阈值。
- **D7 参数与改动面**：窗口 N 默认 5、空闲阈值默认 10 分钟、聚合输入 token 预算封顶（约 4k，超限提前切段沉淀），全部进 config.yaml memory 区块可调。改动面：runtime 入队点、jobs（batch extract 形态、幂等 key = conversation + 起止 sequence + policy version）、worker 空闲扫描、现有单消息 extract 相关测试重写（归 `tests/memory/`）。

**术语**：沉淀（consolidation）已入 CONTEXT.md（显式即时、隐式沉淀双轨）；**ADR-0008** 记录决策与动因。

**实现落地（2026-08-29）**：按本票决议（D1–D7）实现（执行 agent dsv4f，交接文档已弃置），主会话验收通过：pytest 430 用例全绿（执行报告的 10 个失败经复核全为环境性）、ruff 干净、schema v13 经 migrate 落库、端到端实弹验证窗口触发与 600s 空闲兜底均正确（游标推进、事实写入、source_ref 窗口级）。行为语义留档：访客不写长期记忆（旧行为一致）、job 终态清空 content（既有隐私设计）、失败 run 消息不入游标。执行报告与交接文档按用户要求弃置，细节以本票 + ADR-0008 + 代码为准。
